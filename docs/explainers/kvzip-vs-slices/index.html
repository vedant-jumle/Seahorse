Why does KVzip’s sparse cache keep the model answering?

Seahorse stores a memory as a slice of a frozen model’s own K,V cache and restores it in a later chat. Choosing which few entries to keep is the hard part. KVzip, a published compression method, turned out to choose better than any of our own selectors on three of four models. This page explains how KVzip works, how our slices work, where the two differ, and what our results say about why the difference matters.

Short answer, so far: a sparse slice works when it keeps the entries each attention head will actually read, in proportion to how much that head reads from memory. KVzip gets close to this by letting every (layer, KV head) keep its own entries, chosen by how much the model reads them while copying the turn out again. All of our selectors keep one shared set of positions for every layer and head, and so cannot do this. On Llama-3.2-3B the evidence for this reading is direct. On Qwen2.5-1.5B KVzip fails in the way the reading predicts. On Qwen2.5-7B KVzip wins for a reason we have not measured yet.

Part 1 · prior work

How KVzip works

KVzip (Kim et al., NeurIPS 2025, arXiv 2505.23416) compresses a K,V cache once, before any question exists, so that the compressed cache can serve every later question. Its idea: if the model can still reproduce the context from the cache, the cache still holds what any question will need. So it asks the model to reproduce the context and keeps the cache entries that the reproduction reads.

It runs in four steps.

  1. Store the context. The model reads the text once. Every token leaves a key and a value at every layer and every KV head. For one of our stored turns on Llama-3.2-3B that is 28 layers × 8 KV heads = 224 entries per token.
  2. Ask for an exact copy. After the stored text, a new turn asks Repeat the previous context exactly. The reply is not generated. It is the stored text itself, fed in as if the model had written it (teacher forcing), so one forward pass covers the whole copy.
  3. Score every entry by its peak attention. While copying, each new token attends back to the stored cache. To write the 40th word of the copy, the model mostly reads the 40th word of the original and its neighbours. An entry’s score is the largest attention it receives anywhere in this pass: the maximum over every row of the copy (and the request) and over every query head that shares its KV head.
  4. Keep the best entries. The top-scored entries stay; the rest are dropped. The unit kept is one (layer, KV head, position) entry, not a whole token.

Step 4 can be done three ways, and the difference between them is the subject of this page. We ran all three.

Why copying is a fair stand-in for future questions. A question about the turn will read some part of it, but we don’t know which part. Copying reads all of it, and the paper shows that entries the copy needs heavily are the ones real questions, summaries and reasoning tasks also read (their Figure 6, on SQuAD with Llama-3.1-8B). Copying is a single question-free pass that covers the reads of many possible questions at once.

A side effect the authors report. In their Table 1, Llama-3.1-8B with the full cache refuses to give a phone number from the context (“I cannot provide personal contact information.”). With a 40% KVzip cache, it answers with the number. Compression changed whether the model was willing to answer, separately from what it knew. Our refusals go the other way (the slice holds the answer, and the model declines), but the lesson is the same, and it is central to Part 4.

Technical: the score, and our reimplementation

For layer l and KV head h with G grouped query heads, input = repeat prompt + context (length nin), stored context length nc, softmax over the full key set:

Sl,h[i] = maxg = 1..G maxt = 1..n_in softmax(Ql,h,g KlT)[t, i],   i = 1..nc
  • Global budget: keep the top N = k × E entries over all (l, h, i), E = Σl (KV heads at l) = 56 / 112 / 224 / 512 entries per position on Qwen2.5-1.5B / Qwen2.5-7B / Llama-3.2-3B / Granite-4.2-30B. Some heads keep nothing. Per head: top k per (l, h). Shared: top k positions of the mean of S over all (l, h).
  • KVzip scores in 2K-token chunks with the prompt “Repeat the previous context exactly.” (later chunks: “Repeat the previous context starting with ⟨last 8 tokens of preceding chunk⟩:”). Cost ≈ 2× the initial prefill (paper, Fig. 8).
  • Our reimplementation (experiments/dream_compare/baselines.py, stage_a.py::sel_kvzip) follows the official attention/score.py::_get_score, because the official code needs flash-attn (fp16/bf16, Ampere only) and a custom kernel. Disclosed differences: the repeat request is a new user turn (our stored turn is a closed chat turn); fp32 eager attention; no chunking (our longest turn, 1,040 tokens, is below the 2K chunk); our chat-template head acts as the attention sink.
  • How a per-head slice is run: the whole stored turn stays in the cache and, per (layer, KV head), the slots that head does not keep are masked (expanded to the query heads of its group). Tested: keeping everything equals the full cache; the same picks in every head equal the physical splice. Budgets are matched in stored entries, so every slice holds exactly k × E entries.
Part 2 · Seahorse

How our slices work

Seahorse keeps a memory as a slice: the key and value that a few chosen tokens left at every layer when the model first read the turn. In a later chat, the slice is placed back in the cache at the tokens’ original positions (their stored RoPE positions), after the chat-template head. The new question starts where the stored turn ended, so to the model the gap looks like tokens it can no longer see, not like a shifted sentence. With every position kept, this is exactly the same as having the turn as earlier text (logits agree to within 5×10−4 on every model we checked).

Which positions to keep is the selection problem. We built four selectors. None sees the later question.

Most-attended in turnno extra pass

Keep the positions that the turn’s own later tokens attend to most, averaged over heads and layers. The H2O family.

Repeat-attention, sharedour weaker KVzip-like proxy

Ask the model to repeat the turn (teacher-forced, as KVzip). Keep the positions with the highest mean attention from the copy, averaged over all heads and layers.

Guessed-question attentionmain bet of automatic selection

The model writes 3 questions it expects about the turn. Keep the positions those questions attend to most, averaged over heads and layers.

Drop-one testexpensive; behaviour, not attention

The model answers its own guessed questions. Remove each position in turn; keep the ones whose removal hurts those answers most.

Common to all four: each produces one score per position, and keeps the same k positions in every layer and every KV head. That is the “shared positions” shape of Part 1. Even our repeat-based selector differs from KVzip twice: it averages where KVzip takes a maximum, and it shares positions where KVzip keeps entries.

Technical: the selectors exactly
  • Most-attended in turn: mean attention a content position receives from later content tokens of the same reading pass (mean, not sum, against early-token bias), averaged over heads and layers.
  • Repeat-attention, shared: after the stored turn, “Please repeat exactly what I just told you.” + assistant header + the turn’s text, teacher-forced; mean attention from the copy rows only (not the request) to each content position, averaged over every head and layer.
  • Guessed-question attention: the same model, greedy, with a fixed prompt (instruction + two invented examples) writes 3 questions; attention from each question’s tokens and its last prompt token to each content position, averaged over heads and layers, summed over the questions.
  • Drop-one test: drop in log P(the model’s own greedy answer to each guessed question) when one content position is removed, summed over questions; only on turns of ≤ 200 content tokens.
  • Selectable positions are the turn’s content tokens only (not the role header or end token). The chat-template head is always kept and not counted.

Part 4 · what our runs show, in order

The results, in context

Four experiments, run in this order between 4 and 12 November 2026. All use LongMemEval: one user turn that holds a fact is stored; later the benchmark question is asked with only the slice in the cache. Answers are generated (1 greedy + 4 samples) and judged by LongMemEval’s own prompt with three judge models (majority label). The budget is “8 positions’ worth” (k = 8 × E entries) unless stated.

4a · Automatic selection: works a little, and exposes the licence problem

Our selectors beat random but recovered only a small part of what the whole turn gives. The more important finding came from the label-cheating slice that keeps the answer tokens themselves. Scored teacher-forced (the model is made to say the answer, and we read its probability), that slice recovers most of the whole turn: 0.99 of the gap on Qwen2.5-1.5B, 0.88 on Qwen2.5-7B, 0.67 on Llama-3.2-3B. In free generation the same slice is judged correct only 0.17 / 0.49 / 0.24 of the time, mostly because the model declines (“I don’t have information about…”). The memory holds the content; the model does not take it as licence to answer.

4b · Selector comparison: KVzip with a global budget wins on three of four models

We then ran the published selectors against ours at matched budgets (106 items, four models). KVzip with its global budget was the best question-free selector on Qwen2.5-7B, Llama-3.2-3B and Granite-4.2-30B, judged correct 0.42 / 0.41 / 0.63 where the whole turn gets 0.67 / 0.59 / 0.67. On Granite it is above even SnapKV given the real benchmark question (0.63 vs 0.58). On Qwen2.5-1.5B it does not win: 0.10, against 0.16 for the drop-one test and for Expected Attention.

Across methods, per head beat shared positions on Qwen2.5-7B and Granite (for all three methods tested both ways), not on Llama or the 1.5B. The real KVzip also beat our repeat-attention proxy on three of four models, so the proxy was a weak version of the idea.

Technical: rules and per-head vs shared differences

Pre-registered at k = 8, generation, three-judge majority, 106 primary items (not abstention, not preference); paired item bootstrap, 2000 replicates. “Per head beats shared” holds on a model if ≥ 2 of 3 methods have a CI above 0. The best KVzip form on the 1.5B was per head (0.14), still not above repeat-attention, shared.

4c · Head analysis: why does the global budget work?

The obvious explanation was a gate: a few attention heads decide “answer or refuse”, and KVzip’s uneven budget happens to feed them while shared positions starve them. We pre-registered three tests of this on Qwen2.5-1.5B, Qwen2.5-7B and Llama-3.2-3B (66 items, teacher-forced, judged labels reused from the selector comparison). All measurements are at the last prompt token, where the first answer token is decided.

So the gate story is closed. The decision to answer is real and graded, and it rises with how much of the whole turn’s effect gets through, spread over many heads. That pointed to a simpler question, asked as an exploratory follow-up (chosen after seeing the above, not pre-registered): does KVzip’s uneven budget follow where the model actually reads memory? For each item we compared KVzip’s budget per (layer, KV group) with how much attention the last prompt token pays to the stored turn in that group when the whole turn is present. And we scored every slice by mass-weighted coverage: the share of that memory attention the slice preserves, with heads weighted by how much they read memory.

Technical: the three tests, definitions and the causal check
  • The answer direction (code d_comply): at each layer, the mean block output at the last prompt token for general questions the model answers minus personal questions it refuses (66 pairs, no memory). A slice’s position on it = the projection at a readout layer chosen on the other half of the items. Nothing is added to the model; the direction is only read.
  • Test 1, “the decision is a graded direction” (code H-A): per item, Spearman between that projection and first-token refusal mass over no memory, whole turn and the 7 selections at k8. Holds if the mean ≤ −0.4 and the CI is below 0. Result: .
  • Test 2, “a few heads carry it” (H-B): direct attribution of each query head onto the direction; the 8 heads with the largest whole-turn-minus-no-memory push, chosen on one half, must carry ≥ half of the positive push on the other half. Result: . The two halves chose overlapping head sets on Llama (Jaccard 1.00) but different ones on the Qwens (0.14, 0.33).
  • Test 3, “KVzip wins by feeding those heads” (H-C): (i) KVzip global’s coverage of those heads must exceed each shared selector’s; (ii) coverage of those heads must track refusal and correctness better than coverage of all heads. Both fail on all three models.
  • Causal check (exploratory): hiding the whole turn from those heads’ KV groups raises first-token refusal on the 1.5B by (layer-matched control heads ); on the 7B and Llama it does nothing ().
  • Mass-weighted coverage: per (layer, query head), the share of its whole-turn attention to the turn’s content that falls on entries the slice keeps for its KV group, averaged with weights = that head’s whole-turn attention mass on memory. Cross-model verdict for the pre-registered part: “in between” (Test 1 holds on 3 of 3; Tests 2 and 3 fail on 3 of 3).

4d · Memory-system comparison: cache is never better than text

Separately, we compared whole memory systems on five benchmarks with retrieval held fixed (BM25, the same 3 or 10 turns). Cache retrieval restores the retrieved turns’ full cache; text retrieval puts the same turns in as text. Same tokens, same positions; only the encoding context differs. Pooled over benchmarks, cache retrieval is worse than text in 6 of the 8 model × depth cells, equivalent in 1 and inconclusive in 1. It is never better.

That leaves one reason to store cache at all: it skips the question-time prefill of the retrieved turns. On Qwen2.5-7B and LongMemEval with 3 turns, time to first token falls from 0.59 s to 0.11 s. But the full cache costs about 720 MB per conversation against 0.03 MB of text. A cache memory only makes sense if it can be compressed far below the whole turn while still answering, which is exactly the selection problem above. The sparse cache we ran there (8 guessed-question positions per turn) is 32× smaller than full cache and answers far worse (0.15 vs 0.43). KVzip’s global budget was not part of that run.

LongMemEval oracle (500 items), 3 retrieved turns. Text = text retrieval; cache = cache retrieval (whole turns); sparse = sparse cache (8 per turn, guessed-question picks). Storage = mean at-rest bytes per conversation. Granite’s BEAM split is partial (64 of 320 items); Gemma-4 never ran.

4e · The open point

Qwen2.5-7B is not explained. On the 66 head-analysis items, KVzip with a global budget is the best slice there (judged 0.59; drop-one test 0.55; KVzip shared 0.37). Yet first-token refusal is the same for every selector (0.05–0.08), its position on the answer direction is worse than the drop-one test’s, and nothing measured at the last prompt token predicts which slices get judged correct. Its budget leans to late layers (early / mid / late 0.29 / 0.32 / 0.40). Every measurement in the head analysis was taken at the last prompt token. If the 7B’s gain comes from what the model reads while writing the answer (fetching the value, not deciding to answer), those measurements cannot see it.

Part 5 · takeaways

What we know, what is ours, what is open

The principle so far

A sparse slice works when it keeps the entries each head will actually read, weighted by how much that head reads from memory. KVzip’s global budget approximates this through the copy task’s peak attention. The approximation is good on Llama-3.2-3B, poor on Qwen2.5-1.5B, and on Qwen2.5-7B it seems to matter during the answer rather than before it. Shared positions cannot follow this at all, because they force every head to read the same tokens.

Prior work

Known before us

Copy-based, question-free scoring with a global head budget (KVzip). Non-uniform head budgets as the biggest single factor in compaction (Attention Matching’s ablation; also KVzip and the KV-eviction gating paper). Self-generated questions adding little over a repeat prompt (Attention Matching). Compression flipping a refusal (KVzip Table 1). Compressed caches failing to use evidence that survived (Compression-Aware Abstention).

Ours

From our own runs

Restoring 2–8 positions of a turn across sessions at their stored positions. The same-item split between teacher-forced and judged scores, with refusal as the failure. The answer decision read as one graded direction that slices move along, not a few-head gate. KVzip’s budget tracking memory reads on Llama (exploratory). Cache never beating text at fixed retrieval.

Open

Next questions

Probe the 7B at the answer tokens: does KVzip’s late-layer budget serve the value fetch? Select for what heads will read: score entries by the attention mass the model pays them while answering a guessed question, per head, and test it on the 1.5B where KVzip fails. A mass-preserving correction (Attention Matching’s per-entry bias) is the cheapest related test.
